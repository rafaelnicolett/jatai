# Golden master: gerador e CLI de estado

Rede de segurança da F0.4 (lane A) da iniciativa `mod-missao-open-source`. Congela, byte a byte:

- **o que a metodologia instala no workspace do usuário**, pelos pontos de entrada reais que a extensão chama: `StructureGenerator.generate()` (greenfield), `installAgentStructure()` (brownfield) e `migrateKit()`;
- **o que o CLI `helyx-state` responde e grava**: exit code, stdout, stderr e os arquivos resultantes.

É a prova mecânica do Parallel Run (ADR-0012): refactor do Epic 3 = golden idêntico; troca de marca da F1.3 = golden idêntico depois da normalização de marca.

## Rodar

```bash
npx vitest run --no-cache tests/golden
```

| Arquivo | O que testa |
|---|---|
| `generator.golden.test.ts` | 53 casos do gerador (casos em `lib/generator-cases.ts`) e asserções `@known-bug` pontuais |
| `cli.golden.test.ts` | 41 cenários do CLI (em `lib/cli-scenarios.ts`), rodados no bundle do kit **e** num build novo de `src/cli`, e o teste de drift entre os dois |
| `harness.test.ts` | o próprio harness: regras de `normalize()`, o gancho `normalizeBrand`, escape de paths, troca de marca de ponta a ponta |

## Layout dos goldens

```
__golden__/generator/<caso>/tree.json         entrada, resultado, chamadas à TemplateSource plugada e a árvore
__golden__/generator/<caso>/files/<path>      cópia normalizada e legível (texto ≤ 64 KiB)
__golden__/generator/<caso>/views/<path>.txt  visão legível de binário (hoje nenhum caso usa)
__golden__/cli/<cenário>/result.json          passos (cwd, argv, exit, stdout, stderr) e a árvore do sandbox
__golden__/cli/<cenário>/files/<path>         conteúdo final dos arquivos
```

- **Uma linha por path** em `entries`: `dir`, `file <modo> <bytes> <sha256> text|binary`, `file <modo> kit-cli-bundle`, `file <modo> kit-mcp-bundle` ou `symlink -> <alvo>`. Diretórios terminam em `/`, inclusive os vazios.
- **Modo estilo git:** só o bit de execução (`100755`/`100644`). No Windows o modo não é comparado.
- **Base + delta:** um caso com `base` guarda só o que difere da base (`"absent"` = não existe neste caso). Uma mudança no kit aparece nos 4 casos-base, e não nos 53.
- **Cópia legível uma vez só:** cada conteúdo é copiado no primeiro caso (na ordem de `GENERATOR_CASE_ORDER`) que o tem. A comparação usa só os sha256. A cópia serve para o diff do PR e para o relatório de falha, que mostra a primeira linha divergente.
- **Nunca copiado:** o que estiver em `NO_READABLE_COPY` (`lib/golden-store.ts`), para conteúdo de terceiro que não pode ser duplicado. O sha256 continua congelado. Hoje a lista está vazia: o tema pago de terceiro que motivou a regra saiu do kit na F2.3.
- **Escape de nomes:** `.claude`, `CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `.cursorrules`, `.gitignore`, `.gitattributes`, `.gitmodules` e `.git` ganham o sufixo `.golden` nas cópias. Sem isso, o git aplicaria `.gitignore` aninhado aos próprios goldens, e agentes que trabalham neste repo leriam `CLAUDE.md`/`AGENTS.md`/skills aninhados como instrução.
- **O bundle do CLI** (`.github/scripts/helyx-state.cjs`) entra como `kit-cli-bundle`. O arquivo instalado tem que ser idêntico a `kit/scripts/helyx-state.cjs` e manter o modo `100755`. Os bytes do bundle não ficam congelados aqui, porque mudam a cada rebuild de `src/cli`, até num refactor puro. O comportamento dele é congelado pelo golden do CLI.
- **O bundle do servidor MCP** (`.github/scripts/helyx-mcp.cjs`, ADR-0025) segue a mesma regra e entra como `kit-mcp-bundle`: idêntico a `kit/scripts/helyx-mcp.cjs`, modo `100755`. O comportamento dele é congelado pelos contratos MCP (`tests/contract/mcp-tools.contract.test.ts`).

## Normalização (`lib/normalize.ts`)

São as únicas fontes de não-determinismo toleradas. Aplicadas nesta ordem:

| # | Regra | O que faz |
|---|---|---|
| 1 | `eol` | CRLF → LF. Vale só para o gerador, porque o checkout do kit no Windows pode converter. O CLI é pinado com `\r` |
| 2 | `roots` | pasta temporária absoluta → `<SANDBOX>`; o bundle em execução → `<CLI>`. Cobre o realpath (`/private/var` no macOS), `/` e `\`, e a forma escapada em JSON |
| 3 | `brand` | marca atual (a do `src/data/brand.json`) → marca do golden (Helyx) |
| 4 | `generated-by-ts` | `# Generated by <marca> on <ISO-8601 com ms>` → `<TS>` |
| 5 | `resolved-at-ts` | `resolvedAt: "<ISO-8601 com ms>"` → `<TS>` |
| 6 | `run-event-ts` | `"timestamp":"<ISO-8601 com ms>"` de um evento em `runs/*.jsonl` (F5.2: o CLI grava um evento a cada escrita de estado, com o relógio) → `<TS>` |
| 7 | `kit-version` | `kit_version: "<versão exata do package.json>"` (YAML) e `"kit_version": "<versão>"` (lock do kit) → `<KIT_VERSION>` |
| 8 | `temp-names` | `.helyx-tmp-<epoch ms>` → `<TS>`; `.<arq>.tmp-<pid>-<hex>` → `<PID>-<RAND>` |
| 9 | `node-pid` | `(node:<pid>)` → `(node:<PID>)` |

- **stderr do CLI:** num crash do Node, o golden guarda só a assinatura `<UNCAUGHT> <Erro> [<código>]: <mensagem>`. O stack, o trecho de código interno e a versão do Node mudam por versão e por SO. Em log comum, só os frames `at ...` saem.
- **As regras 4 a 7 casam só o formato exato de hoje.** Um `kit_version: "0.0.0"`, que é o que o `kitVersion()` devolve se o pacote mudar de nome sem ajuste, não é normalizado, e o golden falha. Por isso a versão é lida do `package.json`, e não da função de produção.

## Atualizar um golden, de forma deliberada

```bash
UPDATE_GOLDEN=1 npx vitest run --no-cache tests/golden
git diff --stat -- tests/golden/__golden__
```

- **Só localmente.** Com `CI` definido, o `UPDATE_GOLDEN=1` lança erro.
- **Só o arquivo inteiro.** Se faltar algum caso (por exemplo, rodando com `-t`), a escrita é recusada, porque apagaria os goldens que não rodaram.
- **O grupo é regravado inteiro** (`__golden__/generator/` ou `__golden__/cli/`), com escrita em pasta temporária e troca no fim. Casos removidos somem; o teste de integridade acusa caso órfão e cópia faltando ou adulterada.
- **Política (ADR-0012, §4.4):**
  - PR de refactor não altera golden.
  - PR de comportamento altera golden e explica cada arquivo do diff.
  - A correção de um `@known-bug` inverte o teste pontual correspondente e atualiza o golden no mesmo PR, que é só daquela correção.
- **Depurar:** com `GOLDEN_KEEP_SANDBOX=1`, as pastas temporárias ficam em `os.tmpdir()`, com prefixo `golden-`.

## Troca de marca na F1.3 (`lib/brand.ts`)

`normalizeBrand(texto, { from, to })` troca os tokens de uma marca pelos de outra, preservando a forma:

- `helyx`, `HELYX`, `Helyx` e o nome de exibição com acento (`Jataí`, inclusive em NFD);
- em conteúdo **e** em paths: `helyx.config.yaml`, `helyx-state.cjs`, `/helyx`, `@helyx`, `helyx.agent.md`, `HELYX_*`, `.helyx-tmp-`, `helyx-template-`.

Sem marcas, ou com a mesma marca nos dois lados, é identidade. Desde a F1.3, `CURRENT_BRAND` é lida do `src/data/brand.json` e os goldens continuam em `HELYX_BRAND`.

Na F1.3 (feito; o passo a passo fica como referência para uma próxima troca):

1. Conferir `JATAI_BRAND_DRAFT` contra o `brand.json` real. Tokens extras entram em `aliases`, com a mesma chave nas duas marcas.
2. Trocar a marca no `brand.json` (o `CURRENT_BRAND` lê de lá). Os paths do kit seguem a marca: o bundle passa a ser `kit/scripts/<slug>-state.cjs`, e as fixtures usam `CURRENT_BRAND` em `<slug>.config.yaml`, `/<slug>`, `<slug>.agent.md` e no marcador do `.gitignore`.
3. Rodar `npx vitest run --no-cache tests/golden` **sem** `UPDATE_GOLDEN`. Toda saída é normalizada de volta para Helyx e comparada byte a byte com os goldens atuais. Passar = só a marca mudou.
4. O relatório "mudou só por marca" é o campo `brandOnly` de `TreeGoldenGroup.compare()`: paths cujo conteúdo só bate depois da regra `brand`. O `harness.test.ts` exercita esse fluxo de ponta a ponta, com uma instalação brownfield trocada para Jataí.
5. Fora da árvore, os snapshots de caracterização e de contrato usam `goldenBrandSnapshotSerializer`, e as listas pinadas usam `toGoldenBrand` (`lib/brand.ts`): toda string entra na marca do golden antes de comparar.
6. Os goldens **não** são regravados na F1.3. Regravar com a marca nova é um passo posterior, quando a marca antiga deixar de ser referência.

## Isolamento e determinismo

- **Rede:**
  - Desde a F2.1 o gerador não tem registry nem cache de templates (ADR-0015). Os casos locais usam a `NullTemplateSource` padrão; os casos zip injetam uma `TemplateSource` falsa em `generator.golden.test.ts`.
  - O `fetch` global vira erro nesse arquivo.
  - O CLI roda com ambiente por allowlist: sem `HELYX_*` e sem `NODE_OPTIONS`, e com HOME no sandbox. Assim o cliente do State Service não acha `server.json` e não abre socket.
- **Disco:** tudo é escrito em `os.tmpdir()`. A exceção é `__golden__/`, e só com `UPDATE_GOLDEN=1`.
- **Sem SQLite:** desde a ADR-0017 (F3.3) o estado é só YAML; o greenfield não ganha mais `.github/artifacts/.state-service/state.sqlite`, e o caso `greenfield-claude-padrao-sem-wasm` saiu junto.
- **Zip-fixture:** datas fixas e `STORE`, então os bytes são estáveis.
- **Ordem:** o walk ordena por nome (code units); as fixtures são escritas em ordem.
- **Repetição:** a suíte roda várias vezes seguidas sem diferença. Há testes explícitos de determinismo (mesmo caso gerado duas vezes) e de idempotência do `migrateKit`.
